## 背景と仕組み

固定長のEntityプールでは、空いている要素のインデックスを配列に並べ、`free_count` で有効範囲を管理できる。末尾から取り出せば後入れ先出しのスタック。先に入れた値から取り出すキューは先入れ先出しになる。

空き配列に同じIDを二度入れると、容量の範囲内でも同じEntityを二度払い出せてしまう。ここでいう二重返却は、プールの利用状態が壊れる現象。対策案は使用中フラグを持ち、使用中のIDだけを返却として受理すること。払い出しと返却の両方でフラグを更新する。古い参照が再利用後に残りうる設計では、世代番号も検討できる。

## 空き数とスロットの状態を照合する

`free_slots[0..free_count)` の各IDは範囲内で一意であり、使用中のスロットを含まない。これを払い出しと返却の両方が守れば、同じスロットを同時に2つの用途へ貸し出さずに済む。次は単一スレッドで返却を検査する説明例。

```c
bool release(Pool *pool, size_t id) {
    if (id >= CAPACITY || !pool->active[id]) {
        return false;
    }
    pool->active[id] = false;
    pool->free_slots[pool->free_count++] = id;
    return true;
}
```

世代番号を使う場合は、呼び出し側のハンドルにIDと世代を持たせる。返却して同じIDを再利用した後は、前の世代のハンドルを拒める。使用中フラグだけだと、再利用済みのIDを指す古いハンドルを区別できない。

### 配列の有効範囲を追う

実装の容量を3に縮めた説明例。空きIDは `free_slots` に格納し、弾とそのEntityは別の固定長配列 `missiles[id]` に置く。表の最終列は、Entity配列の添字0、1、2の順で `active` を並べたもの（○は使用中、–は空き）。空きIDの右端が次に払い出すID。空き数は `free_count` の値。IDはこの配列の添字。払い出しは `free_slots[--free_count]`、返却は `free_slots[free_count++] = id`。返却処理は最初に対象の使用中フラグを落とす。

| 操作 | 空きID | 空き数 | 使用状態 |
| --- | --- | ---: | --- |
| 初期状態 | [2, 1, 0] | 3 | [–, –, –] |
| ID 0 を払い出す | [2, 1] | 2 | [○, –, –] |
| ID 1 を払い出す | [2] | 1 | [○, ○, –] |
| ID 1 を正常に返す | [2, 1] | 2 | [○, –, –] |
| 検査なしで ID 1 を再度返す | [2, 1, 1] | 3 | [○, –, –] |

払い出しで消えるのは空き配列の**有効範囲**からだけ。配列内の値そのものは残る。`active` を検査する説明例では、最後の行の操作は失敗し、直前の状態を保つ。

検査なしで容量内に重複した場合、次の2回の払い出しが同じ `missiles[1]` を更新し、先の割当を上書きする。一方、空き数がすでに3の状態でさらに返却すると、`free_slots[3]` への書き込みが範囲外となる。これはCの未定義動作なので、その後の配列やプログラムの状態は予測できない。

世代番号を使う設計では、たとえば ID 1 の古いハンドルが `(1, 7)`、再払い出し後が `(1, 8)` なら、使用中のIDでも `(1, 7)` の操作を拒否できる。参照の取得と返却の両方でID・使用中フラグ・世代を確認する。比較を通すだけでは直接保持したポインタを無効化できず、世代が周回すれば同じ値を再利用するため、ハンドルの保持期間に合うビット幅と周回時の扱いも決める。
